How Comet Hunt fits together

Everything we run lives on Cloudflare: the site, one API Worker, a database and a file store. The heavy science data never passes through us. The sky pictures and the SPHEREx photos go straight from NASA's public servers to the visitor's browser, and the browser does the image work itself. Cloudflare only holds what people add: labels, votes, comments and which patches have been checked.

The steps in the picture

  1. App files. Visiting the site loads HTML and JavaScript from Cloudflare's static assets. No server runs to show a page.
  2. Sky picture. The oval map and the zoomed sky load NASA's all-sky tiles straight from IRSA. These already work today.
  3. Coverage map. One small image saying when SPHEREx first photographed each spot drives the time slider. We build it with a Python script and keep it in R2.
  4. Comets and the heat map. The map asks the API for labeled comets and for how many times people checked each patch, both read from D1.
  5. Photo list. Clicking a spot asks the API which SPHEREx photos cover it. The Worker asks IRSA's search and caches the answer. Works today.
  6. Photo bytes. The browser downloads just the needed piece of each photo from the public AWS bucket, and a Web Worker lines the photos up and subtracts the still stars. Works today.
  7. Known objects. The API asks SkyBoT which known comets and asteroids were at that spot at that time, so the viewer can circle them.
  8. Labels and comments. The browser sends the label or comment with a Turnstile token. The Worker checks the token, then writes to D1 and marks the patch as checked.
  9. Dot finder. Every night a Cron Worker looks at new photos, finds dots that move between shots, and saves them as candidates for people to label.

What we store in D1

Each comet gathers dots across photos; each dot gathers people's labels; each comet has a thread. "Explored" counts power the heat map.

comets

id, name (C-0147), status: candidate, likely comet, confirmed, known

dots

a moving dot in one patch: comet id, photo ids, ra, dec, time, speed, thumbnail key in R2

labels

dot id, user id, kind (comet, asteroid, glitch, not sure), note, time

posts

comet id, user id, reply-to post id, text, time

explored

sky cell, times checked. One row per patch area, bumped when someone labels or marks it done.

users

id, nickname, created. No passwords in the first version (see below).

Decisions to make together

How do people sign in?

Nickname only, with Turnstile: fastest to build and no passwords to protect, but anyone can post as any name.

Sign in with GitHub or Google: real identities and less spam, but a few more hours of work.

Lean: nickname for the demo, with sign-in listed as next.

Where do the dots come from?

Found ahead of time by the dot finder: people label ready-made candidates, so the demo always has something to show.

Found by people while they blink photos: truer to "the public finds them", but slower and harder to demo.

Lean: both. Candidates seed the map, and anyone can add a dot the finder missed.

Do photos go through Cloudflare?

Straight from AWS (today): nothing to pay or cache, and already works.

Copied into R2: survives an AWS hiccup, but means storing gigabytes.

Lean: straight from AWS, with practice patches copied into R2 so the guide never breaks.

Live comments?

Load on open (plain D1): new comments show when you refresh.

Live with Durable Objects: comments appear as people type them, but adds a piece to learn.

Lean: load on open for the hackathon.
